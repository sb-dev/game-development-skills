# Core Skills and Commands Contract

**Version:** 1.0  
**Defined by:** [Stage 11 architecture review](../research-logs/2026-09-13-stage-11-core-skills-and-commands.md)  
**Execution boundary:** [Execution and installation](execution-and-installation.md)

## 1. Installable responsibilities

Select **Hypothesis A: minimal orchestration**, with three independently installable units. Two serve game production and evaluation; the third authors optional specialisation. Three is the result of the responsibility comparison, not a prescribed quota. This contract designs their behaviour; actual skill files, execution and installation are later evidence.

| Skill | Discovery description | Coherent responsibility | Inputs | Outputs and completion |
|---|---|---|---|---|
| `game-development` | Design, build, integrate or refine playable gameplay from a brief or an existing game. Use for game-specific production and targeted implementation changes. | Carry the requested production scope from intent to the necessary playable result and checked correction, preserving accepted work. | Brief or existing project, relevant decisions/behaviour, current finding and available tools/content. Missing material decisions are surfaced, not invented. | Requested thesis/rule/system record, adequate playable proof, integrated change or identified build; actual checks, findings, revisions and limitations. Complete only the requested scope; a design-only request ends with the design. |
| `game-evaluate` | Evaluate gameplay, balance, accessibility or performance evidence and diagnose the smallest responsible repair. Use for a new or existing game, including independent review. | Design and run the relevant checks, interpret observations and produce a bounded diagnosis without silently changing accepted gameplay. | Claim/question, specified behaviour or explicit uncertainty, runnable project/build or other adequate representation, target/cases and available human evidence. | Evidence plan and actual results where executable; scoped findings, collection limits, cause/alternatives, repair recommendation and unresolved proof. A missing runtime or participant is recorded, not simulated as success. |
| `game-extension-pack-creator` | Create or revise a researched game-development Extension Pack with explicit core overrides and comparative evaluation. Use for reusable specialisation, not one game's settings. | Convert a justified specialisation into a source-qualified, inspectable pack and its evidence/readiness record. | Specialisation question, exact core baseline, existing pack if revising, available sources and consumer/evaluation constraints. | A bounded pack-authoring increment with justified behaviour delta, source/evaluation traceability and truthful research/implementation/evaluation/readiness status. Detailed pack contracts are owned by the pack-design stage. |

`game-development` contains the essential evaluation and repair rules needed to complete a production request independently. It may use `game-evaluate` when installed and useful, but never relies on its presence. `game-evaluate` can inspect a project produced without this family; it does not require `game-development` records in a mandatory folder format. The pack creator does not become a prerequisite for normal production or pack use.

There is no new coding agent, engine wrapper skill, scheduler or provider router. An optional orchestration system may invoke these skills, but each works with ordinary project-native artefacts. Core accessibility, evidence honesty, approved-decision preservation and small-scope repair apply to both production and evaluation.

## 2. Skill boundaries and installation

| Skill | Mutation and authority boundary | Self-contained guidance | Independent evaluation question |
|---|---|---|---|
| `game-development` | Make requested game/project changes through existing tools within accepted authority/ranges. Material changes use the existing reopen decision; a command name does not approve publication. | Intent/behaviour/proof decisions, content integration, minimum evidence/repair rules, relevant native execution guidance and output expectations. | Can only this installed skill guide an external consumer from a bounded brief to playable behaviour, detect/repair a real failure and preserve accepted rules? |
| `game-evaluate` | Create evidence records and use bounded test/fixture actions. Do not edit accepted game source or values merely to make an evaluation pass; hand a proposed correction to the authorised implementation work. | Claim/method selection, collection integrity, rule/system checks, human/target evidence limits, diagnosis and relevant execution guidance. | Can only this installed skill evaluate an independently supplied game, find the responsible defect and avoid unsupported experiential or causal conclusions? |
| `game-extension-pack-creator` | Create/revise the requested pack and evaluation material. Do not silently replace supplied books, core behaviour or consumer-approved constraints; readiness is evidence-based. | Its authoring workflow, pack contract, core-baseline comparison rules, source/override traceability and validation/install obligations. | Can only this installed skill author a coherent specialisation and reject unsupported overrides or readiness claims without a source checkout? |

Use a concise SKILL.md with precise discovery metadata and routing. Put substantial conditional operating guidance in that skill's own references; read only those needed by the request. Reference sets are chosen for actual content, not a compulsory folder quota. No executable helper is justified merely by this design. A future helper must be necessary, bundled and executed during validation.

Each skill contains its essential instructions and resource closure. No required references into root research logs, sibling skill folders, the central family repository or developer-only absolute paths. Common non-obvious invariants may be repeated between independent units; do not repeat entire manuals or a large generic workflow in every reference. Installation uses the standard Skills CLI; commands below are **named operations within a skill**, not a new shell executable or command parser.

## 3. Common command contract

A user may invoke a named operation or describe the same task naturally. The skill resolves the requested output and performs only the necessary work. Names aid composition, diagnosis and benchmark addressing; they do not force a linear pipeline for every request.

For the selected operation, identify relevant input revisions, purpose/question, authority and preserved decisions; select the adequate representation and actual tool/context; produce the requested artefact/change/evidence; verify the result with claim-appropriate checks; return identity/paths, findings, limitations and the next unresolved decision. Reuse project-native records rather than inventing a global schema.

Outcomes distinguish **completed within declared scope**, **failed with evidence**, and **blocked by a named required input/capability/decision**. An evaluation may complete with a negative finding; the gameplay claim remains failed or unverified. Do not treat a plan as an executed result, a skipped case as a pass, or successful packaging as installed play. Preserve meaningful failed/rejected alternatives and prior accepted revisions.

## 4. Production commands

| Command | Bounded task and inputs | Output / verification boundary | Why independently useful |
|---|---|---|---|
| `define-game-thesis` | From a brief and constraints, connect players, intended action/experience, loop and evidence questions. | Short identified thesis with assumptions, alternatives and authority; a reviewer can identify the next disputed claim and contrary evidence. No gameplay execution inferred. | Reusable framing before code or a material thesis revision; directly addresses S10-01. |
| `design-mechanic` | From the thesis/current behaviour and a rule question, define entities/state, triggers, effects, feedback and reset. | Implementable normal/invalid/boundary cases with units, ordering and preserved ranges; ambiguous semantics remain explicit. | Local rule definition and repair scope differ from a whole system or runtime build. |
| `model-system` | From member behaviours and goals, explain interactions, resource flows, loops, progression and adverse strategies. | A bounded composition/model with member revisions, assumptions and counterexamples; execute calculation/simulation when the request requires it and label model limits. | Exposes coupled failures that local rules miss; includes defining a core loop without a duplicate record. |
| `build-playable-proof` | From a question, game requirements and available execution path, choose and implement the least costly adequate proof. | Runnable requested scope with input, consequences, feedback, outcome/reset and actual appropriate checks; unresolved human/target claims remain visible. | Converts design into observable play and tests fidelity adequacy; a written plan cannot close this operation. |
| `integrate-content` | From composition and handoff requirements, create/configure a greybox or encounter, or bind supplied content. | Actual integrated scene/game data and runtime checks for relevant traversal, state/timing/cues and dependencies; source versus integration failure owner identified. | Spatial composition and content replacement share an integration boundary; task-specific lenses preserve their different checks. |
| `repair-gameplay` | From a reproducible finding, accepted decisions and authorised scope, diagnose and make the smallest sufficient change, including tuning. | Fault/baseline and repaired result, affected-case reruns, preserved behaviour and keep/revert decision. Out-of-range rule changes require the existing owner decision. | Independent repair/regression operation; a small diff alone is not closure and evaluation need not be repeated wholesale. |
| `prepare-playable-build` | From an identified playable candidate and declared target/purpose, prepare the representative or delivery build. | Versioned built artefact, actual build/run checks, applicable target/quality evidence and reproduction instructions; release destination/authority handled explicitly. | Packaging/target validation differs from exploratory proof; representative and release contexts use the same operation with different required gates. |

For `integrate-content`, choose only relevant lenses: greybox traversal/flow, encounter information and recovery, source/import/runtime consistency, animation/narrative/audio bindings or content replacement. A non-spatial game need not acquire a level. For `repair-gameplay`, ordinary approved tuning is permitted; distinguish a parameter defect from a rule, cue, composition or evidence defect. For `prepare-playable-build`, a release-labelled request does not waive failed quality gates or authorise a public upload beyond the user's scope.

## 5. Evaluation commands

| Command | Bounded task and inputs | Output / verification boundary | Why independently useful |
|---|---|---|---|
| `validate-gameplay` | From specified behaviour/composition and a runnable or explicitly modelled scope, choose rule, transition, invariant and reachability cases. | Actual expected-versus-observed results, invalid/boundary/reset and interaction coverage, setup and limitations. Distinguish runtime from model-only checks. | Unified mechanical oracle and scenario execution; selectable lenses retain precise regression cases without separate wrapper commands. |
| `evaluate-player-experience` | From a specific control, feedback, level-flow, comprehension or feel question, choose adequate observation methods and context. | Measured events where relevant, real participant observations/accounts when required, separate interpretation and unmet evidence. No invented players or universal experience verdict. | Keeps experience questions connected to rules and information while preventing input/capture metrics from substituting for people. |
| `evaluate-balance` | From rules/resources, scenario or telemetry evidence and the intended strategic question, examine flows, incentives, cohorts and alternatives. | Defined units/denominators, collection checks, strategy/model findings, contrary cases and tuning hypotheses with causal/human limits. | Balance diagnosis needs system/strategy evidence that a local rule pass does not provide. |
| `evaluate-accessibility` | From critical tasks, intended inputs/presentation and relevant needs, inspect applicable barriers and alternatives. | Task-linked findings, exercised settings/states, automated and human/device evidence kept distinct, smallest responsible recommendations and gaps. | Cross-cutting access assessment cannot be hidden in an optional pack or a single web score. |
| `evaluate-performance` | From a target candidate, workload and declared budget/question, collect appropriate measurements with existing tools. | Actual target/build/settings, measurement endpoints/overhead, samples/problem intervals, comparison and unsupported hardware/latency claims. | Representative performance evidence differs from correctness, capture and editor convenience. |
| `diagnose-gameplay` | From a finding and accepted expectations, trace likely causes and choose the responsible repair unit. | Evidence-backed cause or bounded alternatives, affected consumers, proposed correction and preservation checks; further evidence when cause is unresolved. | Read-only diagnosis can serve independent review; it does not silently execute the proposed gameplay change. |

Lenses for `validate-gameplay` include rules, state transitions and reachability; for `evaluate-player-experience` they include controls, feedback, level flow and feel. The selected lens and its claim remain explicit in the evidence record and later benchmark case. Combining entry points must not combine incompatible proof standards. Engine-state reads, screenshots and test runners are mechanisms used by these operations, not additional domain commands.

## 6. Pack-authoring command boundary

`author-extension-pack` handles one identified specialisation or revision. It reads the exact core baseline and the requested authoring scope, then produces a source-qualified behaviour delta, explicit overrides/dependencies, appropriate examples/evaluation requirements and accurate readiness state. It must distinguish research, implementation and comparative proof rather than treating a generated pack document as complete capability.

The command exists for reuse and benchmark precision: pack authoring changes reusable production behaviour, whereas a consumer game's configuration changes one game. The detailed staged authoring workflow, five-book selection/reuse rules, override interface and comparison contract are defined by the next pack-design stage. This boundary neither selects a catalogue nor starts per-pack research early. The installable creator must contain that completed guidance before it can be claimed implemented.

## 7. Composition, repair and validation obligations

A production request may compose thesis, rules, system modelling, proof, integration, evaluation, repair and build operations as its scope requires. A request to evaluate an existing game can start directly at evaluation. A request to repair a supplied finding need not recreate the thesis. A request for a brief does not authorise building or publishing a game.

Production owns changes; evaluation owns the scoped judgement and repair recommendation. The same agent/person may perform both roles, but retain the expected behaviour and actual evidence so it cannot silently redefine success after seeing a failure. A public release or material change keeps the consumer's authority; ordinary reversible checks/repairs use already granted authority.

Validate discovery with realistic requests and near-misses, selective installation with each unit's resources, and command behaviour with observable output and contrary cases. Evaluate a wrong-layer repair, stale evidence, missing runtime/human input, source versus integration fault, and accepted-range preservation where applicable. Structural validation is necessary for discoverability but cannot prove decision quality. Later benchmarks must address the selected commands/lenses and expose actual behaviours rather than match instruction wording.

Add a separate skill only when an actual isolation, evaluation, responsibility or substantial conditional-guidance problem requires it. Balance, level design and playtesting remain command/lens responsibilities for now; professional role names alone do not justify new installation units.
