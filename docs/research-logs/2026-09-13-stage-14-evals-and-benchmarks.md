## 3. Core cases and regression design

BC01–BC16 retain accepted source-derived questions with explicit setup/task, expected evidence, faulty alternative, repair and preserved decisions. BC17–BC20 add performance tail/endpoint interpretation, checkpoint-versus-full-reset, disappearing focus and stale/wrong execution context. BC06 includes the four already accepted discipline handoff variants. These are twenty case families; their runtime fixtures remain future work.

Eight SR01–SR08 probes convert the prior routing walkthroughs into future actual installed-skill behavioural checks: bounded thesis, independent production, independent evaluation, source/integration ownership, screenshot/feel claim, change authority, pack authoring and engineering near-miss. The fourteen command mappings in Stage 11/13 remain the operation coverage source. A probe judges actual scope/actions/output rather than keyword matching.

The regression protocol requires the new fixture to fail on the retained faulty state and pass on the repaired state, plus affected-case preservation. Keep deliberate injections and evaluator familiarity explicit. A plan, empty fixture, always-green script, unexplained changed oracle or discarded bad seed fails the intended test. Real escaped defects add the smallest adequate reproduction without forcing a complete campaign run for a local rule failure.

## 4. Budgets and claim validity

Stage 13's numeric project budgets are retained without silent relaxation. They are declared targets for bounded browser examples, not measured baselines or sourced perceptual thresholds. Frame-interval targets approximate 30/20 scheduling opportunities per second while explicitly excluding claims about presented frame rate, physical input latency or unmeasured devices. Simulation/update, generation and network-convergence budgets retain their own endpoints and workloads.

Percentiles use a declared nearest-rank definition with sample count/raw data, stated loading/warm-up exclusions, maxima and relevant stalls. CPU, GPU, memory, allocation, load, streaming, input and network measures need suitable tools and context; missing tooling is unknown, not zero. Appropriate built candidate evidence is required for release-related claims; Editor averages cannot replace it.

BC17's synthetic twenty-sample design analytically has mean 26.5 ms and p95 120 ms, demonstrating why a mean can conceal its 33.3 ms p95-budget failure. This is an expected arithmetic oracle, not an executed profiler or measured game result. Actual target capture remains an owning-stage obligation. Human comprehension, feel, fairness, mastery, flow and satisfaction similarly retain their actual evidence requirements rather than borrowing confidence from technical proxies.

## 5. Pack comparison and installation gates

Both P5 profiles and all **25** cases remain intact: Precision **12**, Tactical **13**. Each implemented pack must run its exact-prompt showcase, distinct reuse, behaviour/precedence cases and fair competent-core comparison. The matched pair uses equal substantive prompt/inputs and comparable settings/tools/resources; only activation and packaged guidance intentionally differ. Record exact contexts, revisions, actual outputs, failures, regressions, contamination and evaluator limits. Add ordinary project instructions or repeated trials when ambiguity, variation or the claimed benefit requires them; retain all outcomes.

A single favourable pair is insufficient by itself. Useful intended specialist effect, independent reuse, preservation, negative cases and clean installed use are separate requirements. If value is absent or indistinguishable, keep the entry unproven/inconclusive or refine a demonstrated recurring weakness. Never impoverish core or enrich the packed task to manufacture benefit. Pack research, implementation, evaluation and readiness remain separate, with no maturity promotion inferred.

Installation design covers production only, evaluator only, creator only, production with a selected pack, evaluator with a selected pack, and the combined/negative installation scenario. Each uses normal Skills CLI installation with recorded versions/options and local resource closure. External projects cannot depend implicitly on source/root docs, books, sibling skills, creator or another pack. Explicitly supplied consumer game/evidence remains legitimate input. Successful source validation and successful external installed execution must have different evidence records.
